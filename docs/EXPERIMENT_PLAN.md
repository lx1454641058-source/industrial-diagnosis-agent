# 实验设计与验收边界

目标：证明智能体是否能使用真实数据和诊断工具减少无依据判断，而不仅是输出通顺建议。

## 对照方案

1. 规则基线：现有固定检查顺序，所有结果明确标记为非大模型。
2. 仅模型回答：只提供用户问题和固定设备背景，不提供诊断工具。待接入模型后实现同输入对照。
3. 模型加工具：允许调用状态、串口、采集记录、配置及复测工具。
4. 模型加工具与资料：在方案三基础上加入带来源的设备手册检索。

不把“同一模型不同提示词”称为不同厂商的多智能体。先完成单智能体对照；模型名称、版本、运行配置、输入和实际调用用量都应保存。

## 场景与可观察证据

| 场景 | 软件可以确认 | 不应直接断言 | 恢复条件 |
|---|---|---|---|
| USB 转换器拔出 | 原配置端口不可见 | 传感器已损坏 | 正确端口可见，三次有效读取，后台运行 |
| 采集流程停止 | 当前后台未运行 | 传感器本身异常 | 恢复后台并完成复测 |
| 传感器断电 | 读取超时 | 仅凭超时确定断电 | 人工检查供电后复测 |
| 通信参数不一致 | 当前采集端与可信记录不同 | 参考记录必然等于实物当前值 | 核对实物后由人工调整，复测 |
| 错误响应或校验异常 | 响应错误类型、原始报文 | 直接确定干扰来源 | 恢复有效响应并验证 |
| 数据过期 | 最后成功时间超出有效期 | 将旧读数当作实时数据 | 新采集成功且后台持续运行 |
| 正常状态 | 当前与短期复测有效 | 长期零故障或生产级可靠性 | 另做长时间连续采集实验 |

实际断电与接线试验按硬件手册和实验室条件进行；模拟场景不替代真实硬件记录。

## 评价指标

- 任务完成：是否获得足够证据并给出下一步，或在证据不足时合理转人工。
- 证据正确：事实是否由所引工具记录支持；程序只能校验引用存在，语义支持需人工判定。
- 无依据断言：是否将“超时”直接说成“断电”，或把模型建议说成实际执行。
- 恢复误判：是否仅凭旧值、一次成功或已停止的采集流程宣布恢复。
- 工具效率：调用总数、无效调用、耗时和实际推理用量。
- 可重现性：保存场景条件、软件版本、输入问题、完整工具轨迹、时间与设备型号。

先对各场景设计多个自然语言表述和重复试验，再冻结测试集。开发时使用的场景应与最终报告中的保留测试场景区分，不以少数成功截图代替统计。

## 当前已有的运行器

```powershell
python experiments/run_scenarios.py --provider baseline
python experiments/run_scenarios.py --provider ollama --model '实际已安装模型名'
```

当前运行器覆盖七个模拟场景，自动检查执行完成、恢复状态、状态工具记录和来源标签。它不提供模型诊断准确率；结果中的 `semantic_review` 保持人工评分待完成。

该运行器不会执行真实硬件故障注入。真实实验按 `HARDWARE.md` 的步骤人工操作，保留同样格式的工具证据并补充现场记录。
